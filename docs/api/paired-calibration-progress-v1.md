# Paired calibration progress v1

Implemented as a proposed read-only companion surface. It reports the managed
Mac's RF learner, not a second phone learner or legacy baseline controller.

`GET /api/v1/room-learner/progress` uses existing sensing-read authentication and
the companion's installation-pinned, owner/account-bound read grant. Neither a
read nor legacy calibration grant permits POST to this route or owner-only
learner controls. The existing selection envelope advertises
`progress_schema: "ruview.room-learner.progress.v1"`. Consumers discover through
that authorized read first, without first parsing an unsupported inner
selection version or requiring a historical selection to match today's room.
An absent discovery field means selection-only;
old TLS policy may reject an unknown progress route with403 before reaching404.
A404 can also degrade to the selection-only view, but privacy/authentication
failures are never a fallback signal. Do not probe owner status.

Success schema: `ruview.room-learner.progress.v1`. The explicit DTO contains:

- Public installation ID, published room binding/revision, context match,
  `runtime_epoch`, `observed_at_unix_ms` and `expires_at_unix_ms`.
- `runtime_epoch` is the existing public calibration process identity. It is
  **not** the learner's private mutation-guard runtime epoch.
- Recorded Train/HeldOut counts for four conditions; these are sealed records
  in the current capture session, not proof of passing accuracy or all history
  in a durable model. Zero temporary records do not mean a model was lost.
- Bounded phase role/label, preparation/countdown/elapsed/target and representative
  counts, plus aggregate source readiness. No source IDs, packet counters,
  RF values or physiological values are included.
- Separate verified qualification and selection summaries, a bounded machine
  blocker and a workflow stage. These do not start a capture, train, qualify,
  select or enable another capability.
  Qualification names the current candidate where available; selection names
  the separate durable selected model. Their model hashes may differ while a
  replacement candidate is being prepared. No candidate means qualification is
  not reported, rather than a claim that an older selected model lost its proof.
- `save_status` is always `not_reported`: model selection does not prove that
  the Mac app's separate durable Room Save transaction completed.

The snapshot expires at most10seconds after observation, shortened by the
existing paired/account grant's expiry. A revoked or expired grant is refused
before response. Consumers must also fence account, transport, installation,
publication, request generation and runtime changes; reject delayed/stale data.
Published binding is held stable through projection. A concurrent learner
context change cannot borrow readiness from the prior source/grid context.
A published-room mismatch withholds counts, phase, source readiness and all
current qualification/selection claims rather than relabelling another room.
A historical selection for another room/context is not reported as this room's
selection and does not alone block setup for the newly published room.

An empty/unconfigured room has null progress fields. An optional durable-proof
readiness field is not implemented by this base producer. The blocker
`training_lineage_not_reported` means only that this view does not report that
lineage; it is not a statement that a stored model or future managed proof is
invalid. Review readiness on the Mac before requesting physical trials.

Privacy mode returns403 with only schema/success/error_code. No owner scope,
mutation guard, trial/session IDs, model weights, private training-proof data,
raw source counters, media or physiology is projected. Unknown/corrupt artifact
readback cannot produce a qualified/current badge.

"Read-only" means no logical capture, model, geometry, checkpoint or Save
mutation. Existing trusted artifact readers still enforce private-directory
security idempotently (0700); this is not a claim of zero filesystem metadata
side effects. The progress method deliberately does not call owner status,
which can write capture checkpoints.

Synthetic producer fixtures are generated by the real HTTP handler test
`companion_integration::paired_progress_auth_tests::export_actual_paired_progress_producer_cases`.
They are software evidence, not physical sensing qualification.
